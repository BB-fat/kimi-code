6	# Generate Changesets
7	
8	`kimi-code` uses changesets to manage versions and changelogs. The current user-facing published package is:
9	
10	- `@moonshot-ai/kimi-code`: the CLI
11	
12	All other `@moonshot-ai/*` packages are treated as internal packages, including `@moonshot-ai/kimi-code-sdk`, `agent-core`, `kosong`, `kaos`, `kimi-code-oauth`, `kimi-telemetry`, and `migration-legacy`.
13

15	
16	## Core Rules
17	
18	1. **Inspect the actual changes first.** Use `git status` / `git diff --name-only` to identify which packages were actually changed.
19	2. **List packages that changesets can release.** If a changed package is ignored in `.changeset/config.json`, do not put that ignored package in frontmatter together with a non-ignored package; changesets rejects mixed ignored/non-ignored frontmatter.
20	3. **Map ignored internal changes to the affected released package.** If an ignored internal package changes CLI output or behavior, list `@moonshot-ai/kimi-code` and describe the actual user-visible or release-artifact change in the changelog text.
21	4. **Internal package source changes that enter the CLI bundle must manually list the CLI.** `@moonshot-ai/kimi-code` inline-bundles `@moonshot-ai/*` source, but those internal packages are devDependencies from the CLI's perspective, so changesets will not automatically propagate bumps. If a change enters the CLI output, list `@moonshot-ai/kimi-code`.
22	   - **Web app (`@moonshot-ai/kimi-web`) changes always enter the CLI bundle.** `@moonshot-ai/kimi-web` is ignored by changesets (see `.changeset/config.json`) and cannot be mixed with `@moonshot-ai/kimi-code` in one changeset frontmatter. Describe the web change in the changelog text, but list `@moonshot-ai/kimi-code` so the CLI release carries the bundled `dist-web` output.
23	5. **Docs-only and tests-only changes usually do not need a changeset.** README, internal docs, and `test/` changes that do not enter package output do not trigger a CLI bump.
24	6. `@moonshot-ai/vis` / `vis-server` / `vis-web` are ignored by changesets and should not be handled.
25	
26	## Workflow
27	
28	1. List the changed packages and check whether each one is ignored by `.changeset/config.json`.
29	2. Choose a bump level for each package.
30	3. If an ignored internal package change enters the CLI bundle, put `@moonshot-ai/kimi-code` in frontmatter instead of mixing the ignored package into the same changeset.
31	4. Create a short kebab-case file under `.changeset/`.
32	5. Split unrelated changes into separate changesets; keep one logical change in one file.
33	
34	Format:
35	
36	```markdown
37	---
38	"<package A>": patch
39	"<package B>": minor
40	---
41	
42	<English changelog entry>
43	```

45	## Bump Levels
46	
47	| Level | When to use |
48	|---|---|
49	| `patch` | Bug fixes; build/package fixes; internal refactors that do not change behavior; wording tweaks; small dependency upgrades; small improvements to existing features with limited user-facing impact (e.g. a new keyboard shortcut, a flag alias, a minor UX tweak) |
50	| `minor` | A substantial new user-facing feature, such as a new slash command, a new built-in tool, or a new mode |
51	| `major` | Breaking changes: incompatible config changes, renamed or removed commands/arguments, behavior semantics changes, and similar |
52	
53	When in doubt between `patch` and `minor`: if the change improves an existing feature and the user-facing impact is small, choose `patch` even when the change is technically "new". Reserve `minor` for a substantial new capability that introduces something users could not do before.
54	
55	### Major Rule
56	
57	Never write `major` on your own.
58	
59	If you believe a change qualifies as major, stop first, explain why, and ask the user for confirmation. Only write `major` after the user explicitly agrees. If the user does not reply, replies ambiguously, or disagrees, fall back to `minor`; if `minor` is also unclear, fall back to `patch`.
60	
61	## Wording Rules
62	
63	- Changelog entries **must be written in English**.
64	- **Keep the whole entry concise.** Aim for one short sentence that states what was done; at most a short sentence plus a one-line usage hint. Do not write a paragraph, do not pile on technical detail, and do not enumerate every sub-change.
65	- **For new user-facing features, append a brief usage hint** so users know how to try it. Keep it to a single short line — a command name, a subcommand, a flag, or a one-line "how to use". Do not explain design rationale or list edge cases. Skip the hint for bug fixes, internal changes, and refactors.
66	  - Slash command: `Add the /foo slash command to list active sessions. Run /foo to see them.`
67	  - CLI subcommand: `Add the kimi web subcommand to open the web UI. Run kimi web to launch it.`
68	  - Flag: `Add a --bar flag to skip confirmation prompts. Pass --bar to skip.`
69	  - Too long: `Add the /foo command to list active sessions. It accepts an optional --all flag to include background sessions, supports filtering by name with /foo <name>, and writes the result to the transcript...`
70	- User-facing CLI wording should only be used when CLI users can perceive the change.
71	- Internal changes that do not affect CLI users can still share a changeset with the CLI, but the wording must describe the real change honestly and must not present it as a user-facing feature.
72	- Do not mention file names, class names, function names, PR numbers, or commit hashes.
73	- Do not include real internal endpoints, key names, account names, or service names. If an example is needed, use neutral placeholders such as `example.com`, `example.test`, or `YOUR_API_KEY`.
74	- Avoid vague words such as `refactor`, `optimize`, and `improve`. Describe the actual change, or use more specific wording.
75	
76	## When You Are Unsure About a Change
77	
78	Generate the changeset from what the diff clearly shows. If part of a change is unclear and you cannot confidently describe what it does for users, do not guess or pad the entry with vague wording.
79	
80	1. Finish the changeset for the parts that are clear.
81	2. Then ask the user once, in a short list: name the specific change(s) you do not understand, and ask whether you may dig into the repository (read related source, tests, or call sites) to describe it more accurately.
82	3. Only read more code after the user agrees. If the user says no or does not reply, keep the concise wording you already have and do not invent detail.

147

150	- Prefix the changelog entry text with `web: ` (for example `web: Fix the chat not scrolling to the bottom after sending a message.`) so the synced docs changelog can mark web UI entries. Apply this whenever the change is to the web project (`@moonshot-ai/kimi-web`).
151	- If a PR ships a web UI feature backed by server API changes that exist solely to power that feature, prefer a single `web:` entry describing what the web user gets. 211	## Red Flags
212	
213	- You are about to write `major` without asking the user.
214	- A new user-facing feature entry has no usage hint, or the hint runs to multiple lines and explains design rationale.
215	- You guessed wording for a change you do not understand instead of asking the user whether you may dig into the repo.
216	- Internal package source enters the CLI bundle, but `@moonshot-ai/kimi-code` is missing.
217	- A changeset frontmatter mixes ignored internal packages with non-ignored packages.
218	- `packages/node-sdk` was not changed, but `@moonshot-ai/kimi-code-sdk` was listed for "internal package sync".
219	- The changelog entry is in Chinese.
220	- The wording claims more than the diff actually did.
221	- The CLI wording mentions internal package names, class names, or PR numbers.
222	- The entry includes real internal identifiers instead of neutral placeholders.
223	- A change that only touches `@moonshot-ai/pi-tui` lists `@moonshot-ai/kimi-code` instead of `@moonshot-ai/pi-tui`, or mixes both packages in one frontmatter.
224	- A web app change entry is missing the `web: ` prefix.
225	- A server/API changeset exists only to back a web feature that a `web:` changeset already describes (use one `web:` entry instead, unless the API has independent user value).
